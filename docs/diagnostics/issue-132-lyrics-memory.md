# #132 歌词页内存滞留修复

问题：[ECHO #132](https://github.com/Moekotori/ECHO/issues/132)。

## 报告证据与定位范围

附件显示 Renderer 的 JS 堆约 866–905 MiB，20 分钟窗口内 private bytes 增加约 96 MiB；主进程基本稳定。当时只有 74 行歌词、28 首队列，队列序列化数据约 53 KiB，图片解码估算约 22 MiB。附件没有 heap snapshot，因此不能仅凭报告断定是漏删监听器，也不能将全部进程占用归因于一个对象。

本地使用生产模式 React 和真实 Chromium、合成歌词与播放状态复现了持续增长。快照中的强引用路径包括：

- RAF → `LyricsView` 的 `syncPlaybackPosition` / `centerActiveLyric` → 不同更新频率的 `useCallback` 共享渲染作用域 → 历史渲染上下文。
- `LyricsPage` 的延迟校准、智能校准 `useMemo` JSX → 按钮闭包 → 共享页面作用域 → 上一轮另一份缓存 JSX，形成历史页面引用链。

订阅数始终为 4，歌词读取和歌词订阅各 1 次。这里复现的是闭包引用链，监听器数量没有随更新增长。

## 修复

- 使用独立作用域中的稳定回调，通过 ref 读取最新已提交状态。保持现有宿主播放时钟和 seek 行为。
- 将校准控件移到 `LyricsTimingControls.tsx`，按钮闭包仅捕获控件参数，避免缓存 JSX 保留整个页面历史。
- 保持同一个逐字动画循环，状态到达时立即同步；暂停、隐藏、卸载仍清理动画与监听。
- 缓存歌词列表与行组件，避免每次播放状态更新重建全部行。
- 逐字高亮用歌词对象身份识别缓存，移除每帧拼接整行时间戳/文字签名的分配。

## 短时验证

运行 `node scripts/check-lyrics-memory.mjs`。需要已安装的 Playwright Chromium；脚本使用合成数据，不读取用户曲库、播放音频或访问用户配置。

回归基线：`d76763aba5443cfb626f420c7e8ed80304903608`。可通过 `--baseline=<revision>` 在内存中打包旧源码，不切换或覆盖工作目录。旧版本应触发保留上下文数量断言。

74 行歌词，16,000 次状态更新，每 2,000 次强制 GC 后采样：

| 指标 | 修改前 | 修改后 |
| --- | ---: | ---: |
| 第一次采样 JS heap bytes | 5,687,004 | 5,448,040 |
| 最后一次采样 JS heap bytes | 10,622,320 | 6,114,948 |
| 采样窗口增量 bytes | 4,935,316 | 666,908 |
| 保留的 LyricsPage 渲染上下文 | 1,300 | 7 |
| 保留的 LyricsView 渲染上下文 | 1,287 | 5 |
| 播放订阅 / 卸载后订阅 | 4 / 0 | 4 / 0 |

本次模拟的堆增量降低约 86.5%。断言使用保留上下文数量，避免把 JIT、GC 和 RSS 的短期波动作为通过条件。这不是用户真实播放场景的总内存降幅，也没有进行长时间实机播放验收。

相关组件、稳定回调与校准操作测试共 42 项通过。完整 LyricsPage/LyricsView 对照测试的原有 16 项失败前后一致，未新增失败（当时 147 项通过）；主要为旧页面/抽屉和搜索接口测试预期。全项目类型检查受缺失依赖及并行的非本次修改阻挡，本次修改文件没有报错。定向 ESLint 无错误，保留 LyricsPage 原有一项依赖警告。
